About DualView UX

DualView UX demonstrates how the same interface can feel radically different depending on the type of visual impairment a user has. Each demo page starts in an inaccessible state and can be progressively improved using the controls panel.

The key insight: accessibility is not one-size-fits-all. A blind user needs structural changes (alt text, semantic HTML, keyboard navigation). A low vision user needs visual changes (contrast, font size, spacing). Both matter.

  • 246 million people globally live with moderate to severe vision impairment
  • 96.3% of home pages fail at least one WCAG accessibility check (WebAIM 2023)
  • 1 in 12 men has some form of colour vision deficiency
  • Inaccessible interfaces exclude users from banking, healthcare, education, and commerce
  • Accessibility improvements benefit all users — not just those with disabilities
  • Contrast: Minimum 4.5:1 ratio for body text (WCAG AA)
  • Text scaling: Content must remain usable at 200% zoom
  • Keyboard navigation: All functionality available without a mouse
  • Alt text: Every meaningful image must have a text alternative
  • Semantic HTML: Correct heading hierarchy, landmarks, and labels
  • Click a persona card above to open the relevant demo page
  • Each demo starts in inaccessible mode — observe the default state
  • Open the Accessibility panel (right side of screen) to toggle features
  • Switch between Inaccessible and Accessible mode using the panel controls
  • On the Blind demo: press Tab to explore keyboard navigation

Low vision and blindness are fundamentally different conditions. A person with low vision can see — but poorly. They benefit from larger text, better contrast, and clearer visual hierarchy. A blind user cannot rely on visuals at all. They navigate using a screen reader and keyboard, and need the underlying HTML to be correct — headings, labels, alt text, landmarks.

A website that adds high contrast solves nothing for a blind user. A website that adds alt text solves nothing for a low vision user who can see the image but cannot read a small caption. Both groups need different interventions.

  • Blind users hear "button, button, button" with no context about what each button does
  • Low vision users zoom to 200% and the layout collapses, overlapping or hiding content
  • Images are announced as "image" with no description — useless to a screen reader
  • Forms become impossible — inputs have no labels, so the screen reader says "edit text, blank"
  • Users cannot navigate by headings because the page uses styled divs instead of semantic HTML
  • The result: users abandon the task and lose independence

On the Low Vision demo, accessible mode restores proper text contrast, increases font size, widens line spacing, and makes links visually distinct. These are CSS-level changes — no content rewriting needed.

On the Blind demo, it swaps vague alt text ("image") for descriptive alternatives, and changes button labels from "View product" to "View: [Product Name]" — so a screen reader user always knows what they are about to activate.

  • Based on secondary research and simulated personas — no formal user testing was conducted
  • The "inaccessible" mode uses CSS to simulate poor design; the underlying HTML stays structurally valid
  • Real screen reader behaviour varies by software (NVDA, JAWS, VoiceOver) and cannot be fully replicated in a browser
  • The screen reader overlay shows the alt attribute content — not a full audio output simulation
  • Keyboard navigation is demonstrated structurally but not exhaustively tested with assistive hardware
